Do not attempt this. There is a high risk that you could permanently damage the device.

Due to the bug-ridden software deployed by JCI on the Mazda Connect (aka MZD Connect) infotainment system (and an apparent disinterest on their part in fixing these bugs despite years to fix them), users are driven to want to modify/replace the software. It is infuriating that an otherwise excellent vehicle is hobbled by an infotainment system that cost less than 1/100th of the vehicle to produce.

The software is brittle and breaks easily, resulting in "bricking" the device.

There is a "failsafe" Linux image (which, per my earlier posting, is anything but failsafe). The name is a misnomer; at best, the "failsafe" is just a method of restoring/upgrading the main application.

To my knowledge, the only way to invoke the "failsafe" is when the first byte of /dev/mtdblock1 (address 0x010000 of the SPI NOR flash) is set to zero. This is performed by the main application after the security/integrity of the upgrade image on the USB flash drive is verified.

The following equipment was utilized:

custom adapter for the "ENET JTAG" edgeboard connector
Bus Pirate
Pomona 5252 SOIC-16 Clip Test Adapter
0.1" female jumper leads

The CMU has an edgeboard connector labeled "ENET" "JTAG" in silkscreen on the top (CPU-side) of the PCB. Pins 1-15 are on the top of the PCB, and pins 16-30 are on the bottom (same side of the PCB as the SPI NOR flash).

It would seem that pin 29 functions as an active-low CPU reset. Connecting pin 29 to pin 24 (ground) causes the current to drop markedly but leaves the power supplies active. There appear to be no thermal hotspots in this mode. However, since this is not documented, there is the chance that this could damage the device.

Leaving the power supply active but the CPU pins in Hi-Z is critical, as programming the SPI NOR flash externally must be done without electrical contention or sourcing current into unpowered ICs.

Connecting these pins by hand is much too risky, in my opinion. Pin 30 is digital power, for example, so the slightest mistake is very destructive. I made a prototype PCB adapter using the Sullins RBE15DHHN edge connector.

The downside of such an adapter PCB approach is that it means removing the CMU PCB in order to install the adapter. This adds handling risk and leaves the CPU and DRAM without heatsinks. (I'm less worried about heatsinks during this SPI programming procedure as the CPU is in reset.) It may be possible to design an adapter that attaches via pogo pins without requiring CMU PCB removal.

The Bus Pirate, connected to the Pomona clip with test leads, allows reading/writing of the SPI NOR flash whilst the CMU is powered but in the CPU reset mode.

Here are the commands that I used on the Bus Pirate:

setting SPI mode (step at a time via the interactive prompt):
m 5 3 1 2 1 2 2

verifying connectivity by reading the SPI NOR flash JEDEC ID:
[0x9F r:3]
returns 0x01 0x02 0x16 (indicating a Spansion S25FL064P)

read the current state of mtdblock1
[3 1 0 0 r:4]
returns 0xFF 0xFF 0xFF 0xFF if booting in the normal, non-failsafe, mode
returns 0x00 0xFF 0xFF 0xFF if booting in the failsafe mode

write mtdblock1 to change to failsafe boot
[6]
[2 1 0 0 0]

It is desirable at this point to repeat the command to read the current state of mtdblock1 so as to verify that the write was successful.

restore Bus Pirate to Hi-Z (via the interactive prompt):
m 1

At this point, the CMU can be powered down and all programming adapters must be removed. It is desirable to place the PCB back in the enclosure so that the CPU and DRAM are on heatsinks. (The failsafe, in particular, is power hungry; there does not seem to be any power-saving throttling of the CPU.)

When the CMU next boots, it will insist on an upgrade. You must follow the Mazda documented procedures for ensuring the power doesn't get disrupted during the upgrade (as JCI's failsafe is prone to failure). In my experience, even Mazda's procedures seem insufficient; it seems like one has to run the engine to ensure the power to the CMU doesn't get turned off in the middle of an upgrade.

There does not appear to be any downside to starting the failsafe without a USB drive connected. It will display the following message until the USB drive is installed.

Interestingly, there is an extra step in the failsafe with the above procedure. The normal upgrade procedure involves the main application performing a security/integrity check of the upgrade before setting /dev/mtdblock1. There must be some sort of message passed (IRAM or the CAN microcontroller or via a temporary file on the USB drive) to indicate whether the security check has been done. If this is not found (in a cold start such as this), the failsafe performs the check independently. I have to wonder if this leaves a security hole if the user were to substitute a different USB drive after the normal app vets a known good image and then does a warm reset.

After the security check, the upgrade process is the same as normal.

At the end of the upgrade, mtdblock1 is re-written back to normal by the failsafe.

P.S.: the above Bus Pirate procedure should also work to reprogram any portion of the 8MByte SPI NOR flash. It would take a non-trivial amount of time to download, and you would want to write/procure software to perform programming rather than issue many, many text commands. For this reason, though, it behooves developers to have backup copies of all /dev/mtdblock* partitions so that they can be re-written should they become corrupted.
